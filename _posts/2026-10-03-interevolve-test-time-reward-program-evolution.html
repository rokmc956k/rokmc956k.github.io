Paper Review · Humanoid Loco-Manipulation · 2026

Project page ↗ arXiv ↗ HTML paper ↗

InterEvolve tackles a practical question in humanoid loco-manipulation: if a pretrained behavioral foundation model already contains a broad motor repertoire, do we need to retrain the controller for every new task? The paper argues that we often do not. Instead, it keeps the motor controller frozen and evolves the reward program that specifies the task at test time.

Core idea: keep the controller fixed; let an LLM revise the structure of a multi-stage reward program, let CMA-ES tune its numerical constants, execute the resulting program through a forward-backward behavioral model, and score rollouts with a fixed verifier.

1. Reward programs as the task interface

Reference trajectories and single goal states are often too weak to describe contact-rich tasks such as reorienting a box onto a different face, pushing an object through a narrow passage, or kicking an object without using the hands. InterEvolve represents a task as a staged program:

\[ P = \left(\boldsymbol{\theta},\{(r_j,g_j)\}_{j=1}^{J}\right), \]

where $r_j$ is the reward for stage $j$, $g_j$ is its stage-completion condition, and $\boldsymbol{\theta}$ contains tunable constants such as weights, tolerances, kernel widths, and thresholds. A task can therefore be decomposed into interpretable phases such as approach → establish contact → lift → transport → release.

2. Forward-backward behavioral foundation model

Searching over rewards would be prohibitively expensive if each candidate required policy retraining. InterEvolve instead uses a forward-backward (FB) representation. A latent variable $\boldsymbol z$ indexes a behavior, while forward and backward maps factorize discounted future-state occupancy:

\[ M^{\pi_{\boldsymbol z}}(d\boldsymbol s'\mid \boldsymbol s,\boldsymbol a) \approx F(\boldsymbol s,\boldsymbol a,\boldsymbol z)^\top B(\boldsymbol s')\,\rho(d\boldsymbol s'). \]

For a new reward $r$, the value function can then be approximated by projecting that reward into the learned latent space:

\[ Q_r^{\pi_{\boldsymbol z}}(\boldsymbol s,\boldsymbol a) \approx F(\boldsymbol s,\boldsymbol a,\boldsymbol z)^\top \widetilde{\boldsymbol z}_r, \qquad \widetilde{\boldsymbol z}_r = \mathbb E_{\rho}[r(\boldsymbol s')B(\boldsymbol s')]. \]

The important systems consequence is that a new reward does not trigger a new RL training run. The system recomputes a latent prompt and immediately tests it in rollout.

Reward inference bank and reward tilt

A fixed replay-state bank is used to infer each stage prompt. High-reward states can be emphasized by a reward tilt:

\[ \boldsymbol z_{j,t}=\operatorname{proj}\!\left(\sum_{n=1}^{N}\alpha_{j,n,t}B(\boldsymbol s_n)\right), \qquad \alpha_{j,n,t}\propto \hat r_{j,n,t}\exp(\beta\hat r_{j,n,t}). \]

This becomes especially useful for rare behaviors such as kicking, where a uniform average over the replay distribution can wash out the few states that actually express the desired behavior.

3. Object-aware residual adaptation

A body-only behavioral model may contain excellent locomotion and whole-body motion priors while still failing to distinguish tasks that differ only in object state. InterEvolve therefore freezes the body prior and adds an object-conditioned residual branch:

\[ \boldsymbol\mu_{\pi}(\boldsymbol o_t,\boldsymbol z)= \tanh\!\left(\boldsymbol\mu_{\mathrm{prior}}(\boldsymbol o_t^{\mathrm{body}},\boldsymbol z)+\boldsymbol\Delta_{\mu}(\boldsymbol o_t,\boldsymbol z)\right). \]

The design is closely related to residual policy learning: preserve a broad, stable motor prior and learn only the additional object-interaction competence needed to disambiguate manipulation tasks.

4. Dual-loop evolution: LLM structure + CMA-ES constants

  • Outer loop — LLM: edits stages, reward terms, and transition logic.
  • Inner loop — CMA-ES: tunes continuous constants such as thresholds, weights, and tolerances.
  • Execution: the frozen controller converts each candidate reward into a latent behavioral prompt and rolls it out.
  • Evaluation: a fixed verifier scores task completion independently of the reward being optimized.
  • Memory: successful programs are stored in a skill library and can seed future tasks.

5. Why the fixed verifier matters

Reward optimization is vulnerable to specification gaming: a candidate can achieve high reward without actually solving the intended task. InterEvolve separates behavior generation from task verification. The reward program may evolve, but the verifier does not. This makes the search objective much closer to externally measured task success than to raw shaped reward.

6. Results

The central empirical message is that reward-program formulation exposes a large amount of latent competence already present in the controller.

SettingSuccess rateInterpretation

Single-stage restriction44.7%Removing staged structure sharply limits complex behavior.
Full InterEvolve86.5%Structural evolution + numerical tuning + staged execution.

On reference-tracking experiments, the evolved formulation also improves held-out task success, showing that the method is not merely a mechanism for symbolic task decomposition; reward evolution can discover corrections that compensate for mismatches between the frozen controller's observations and the desired world-frame behavior.

7. Skill library and composition

Successful programs become reusable skills. A solved program can initialize a new task, supply useful stage structure, or be composed with other behaviors. This gives InterEvolve a second form of learning: the policy parameters remain fixed, but the system-level task repertoire grows through an expanding library of executable reward programs.

8. What I find most interesting

Interpretation: InterEvolve moves adaptation from policy space into task-specification space. For large pretrained robot controllers, this may be a highly efficient place to spend test-time compute: search over compact reward programs rather than repeatedly updating hundreds of millions of policy parameters.
  • Frozen-policy adaptation: a useful alternative when controller retraining is expensive or operationally undesirable.
  • Residual architecture: body competence can be preserved while object interaction is extended.
  • Program search: structure and constants benefit from different optimizers rather than a single monolithic search method.
  • Verification: a fixed task-success judge is essential to prevent reward hacking.
  • Open question: success still depends on whether the pretrained motor model already contains enough relevant behavioral support for the evolved reward to retrieve.
